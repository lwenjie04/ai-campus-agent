# 数智校答 V2 完整开发计划

**编制日期**：2026-10-20  
**计划状态**：待实施，本文不代表相关功能已经完成  
**范围**：现有 Vue Web 产品完整改版；单人全栈开发；用户确认无固定交付日期  
**复杂度**：高（涉及页面、路由、浏览器持久化、异步生命周期及少量服务端扩展）  
**基础工作量**：21–30 个工作日；含约 25% 联调与问题修复缓冲，按 **27–38 个工作日，约 6–8 周**安排。为估算区间，不是交付保证；不含等待外部账号、素材和服务器资源的时间。

## 1. 目标与已经确认的要求

把当前项目改成可使用、可回归、可部署的校园服务产品，覆盖新版所有展示出来的主要动作。

- 设计以[当前 Figma 深绿色版](https://www.figma.com/design/AanmCyrCvXPqzdrzTIlIJu?node-id=10-94)为准：银白背景、深绿主色 #005B46、链接 #00664F、浅绿 #E7F1EC。
- 保留简洁排版，文案使用功能名称和实际状态，去掉口号和夸张描述。
- [交互说明](interaction-flow-v2.md)作为页面、按钮、登录恢复和异常行为的业务依据。
- 桌面与手机浏览器同一套 Web 业务；手机采用来源抽屉、紧凑导航和适配软键盘的输入区。
- 沿用 Vue 3、TypeScript、Pinia、Element Plus、Vite、Node 原生 HTTP、MySQL 和现有检索链路。
- 历史对话先支持当前浏览器多会话与账号隔离，**不承诺跨设备同步**。
- 语音/数字人改成用户按需开启；当前 MP4 + TTS 可复用，不在本次引入 Live2D/Rive。
- 保留官方资料优先、社区内容审核后发布、低匹配时明确无法确认等规则。

本次不扩展 uni-app、小程序、语音识别、复杂智能体、统一身份认证或推荐流。它们各自作为后续独立项目，不让 Web 改版依赖这些工作。

## 4. 技术约定：实现前固定

### 4.1 页面与 API 使用不同命名空间

- 前端页面使用 /、/chat、/chat/new、/chat/:conversationId、/services、/services/:serviceId、/community、/community/posts/:postId、/admin/review、/admin/retrieval。
- 前端 API 根默认 /api；允许明确的绝对 API 根，例如 https://service.example/api。集中处理尾斜杠和旧 localhost 配置，调用者不手拼多重 /api。
- 浏览器调用 /api/auth/*、/api/chat/stream、/api/community/*、/api/tts、/api/kb/download、/api/lightrag/*；新反馈接口使用 /api/feedback。
- Vite dev/preview 只代理 /api。后端直连的旧别名可在过渡期保留，避免误伤现有 uni-app 或外部开发脚本；新版站点不继续把 /chat 与 /community 宽前缀反代到后端。
- Nginx 的 /api/ 走后端，静态资源按文件返回，其他页面路径走 index.html；接口与资源 404 不能被 SPA fallback 隐藏。Node/API 与前端必须按同一发布清单部署。

Vite 按请求前缀匹配代理，命中后不进行页面转换，因此这里必须先隔离 API。[Vite server.proxy](https://vite.dev/config/server-options.html#server-proxy)  
HTML5 history 的直接访问需要服务端 fallback，同时应用内还需未知路由页面。[Vue Router history](https://router.vuejs.org/guide/essentials/history-mode.html)

### 4.2 会话、请求和身份分开管理

建议最小会话字段：schemaVersion、conversationId、ownerScope、title、createdAt、updatedAt、draft、messages。消息需有稳定 messageId、role、content、status、requestId、sources，以及重试关联字段。

- persisted 数据不保存 Promise、AbortController、Audio、Blob 或闭包。
- 运行态以 ownerScope + conversationId + assistantMessageId + runId 定位，旧回调必须验证自己仍是当前运行。
- 状态至少区分 ready/generating/done/error/interrupted；历史数据里遗留的 generating 在刷新后改成 interrupted，不自动重复发问。
- 切换、离开、退出保存草稿并中止旧请求；返回不自动发问或播音。
- 老全局缓存没有可靠账号归属，迁移时不能静默挂到一个新登录账号；保留原副本和确认入口。
- 本地账号隔离用于正常产品流程，不宣称能替代服务端鉴权或抵御拥有同一浏览器存储访问权限的人。
- 存储满额时提示无法继续保存并提供手动清理路径，不静默删除历史。用节流保存，避免每个字符都同步写 localStorage。

### 4.3 登录恢复意图

统一保存 intentId、type、target、createdAt、consumedAt；只支持白名单动作，例如发送、进入帖子、播放某回答、进入后台。

同页已经明确提交的动作，登录后执行一次；刷新恢复先确认。社区路径需统一守卫，returnTo 限站内安全路径。管理员从问答登录仍留在问答；不能用身份变化触发无关跳转。[Vue Router 导航守卫](https://router.vuejs.org/guide/advanced/navigation-guards.html)

已携带的登录凭据过期或无效时，应返回可识别的重新登录状态；不能悄悄改成游客身份并消耗游客额度。该行为在 0.4 定义、3.4 落地，并补充服务端回归。

### 4.4 取消与游客体验额度的默认规则

执行前将以下规则写进 API 合同及测试，避免只做按钮却没有后端语义：

| 请求结果 | 本计划默认结算 |
| --- | --- |
| 尚未产生首段回答，客户端取消/断开 | rollback，释放预留 |
| 已经产生首段回答后，客户端主动停止或连接断开 | commit 一次，使用本次游客体验 |
| 模型/检索服务失败，没有成功完成回答 | 沿用已有失败回退，rollback |
| 正常完成，包括明确的低匹配答复 | commit 一次 |
| 完成与取消竞态 | settled 标记保证只结算一次；完成已生效则不再次回退 |

前端不自行重置服务端额度；取消计费边界由服务端最终状态决定，不能承诺每次网络中断都退回体验。过期连接收尾、HTTP 正常结束与真正异常断开必须区分。还需限制请求尝试频率，不能只限制成功次数。

客户端 AbortController 需要传递到 fetch；服务端已有超时 Controller 还要与客户端断开生命周期整合。[AbortController](https://developer.mozilla.org/en-US/docs/Web/API/AbortController)、[Node HTTP 响应生命周期](https://nodejs.org/api/http.html#class-httpserverresponse)

### 4.5 来源与内容规则

- 给官方、社区、规则回退和 LightRAG 分支使用同一适配合同；保留 sourceId、来源类型、可信链接和附件。
- publishedAt、updatedAt、applicablePeriod 分开；没有明确证据就标记未知，不把文档标题年份当作失效判定。
- 不把检索分数生成的 confidence 数字解释为“回答正确率”。
- 发现来源 URL 可能带有临时登录票据时，按可验证规则规范为稳定链接，不能无差别删除业务 query；必须核对链接还能打开。不把票据复制到文档、日志或前端截图。
- 事项清单只维护用途、入口和提问模板；政策正文优先引用官方来源，避免双份内容长期漂移。

### 4.6 反馈合同

- POST /api/feedback，业务字段为 requestId、value（helpful 或 none）；主体由服务端登录会话或已验证游客 Cookie 得出。
- 新增 chat_request_receipts 与 chat_feedback 增量表，或等价最小表结构。凭据仅存必要的请求归属、完成状态、来源 ID 与时间，不默认收集完整对话。
- 使用主体 + requestId 唯一约束，反馈变更幂等；服务端验证该主体能反馈这次已完成回答。
- 本次游客回答在同浏览器登录后可根据经过验证的游客凭据关联；不能信任客户端提交的 owner/userId。
- 完成结果明确标记 feedbackEligible；旧消息没有可验证凭据时不显示能写入反馈的假入口。
- 数据库不可用时返回明确失败；真实环境不能提示成功后只写进进程内存。测试可显式启用内存替代。
- 请求凭据写入失败不应把已经完成的问答改成失败：回答继续展示，feedbackEligible 为 false，服务端记录可定位错误；反馈存储恢复后再开放可记录入口。

## 6. 测试与验收策略

### 6.1 按风险选择验证方式

- 视觉、间距、静态导航文案：用真实浏览器截图核对，不为简单颜色或 CSS 类名写镜像测试。
- 会话迁移、身份隔离、恢复动作只执行一次、请求取消竞态：用 Vitest/Pinia 测试真实状态转换和边界。每个测试使用独立 store、时钟与存储，避免测试之间互相污染。[Pinia store 测试](https://pinia.vuejs.org/cookbook/testing.html)
- 服务端鉴权、额度结算、取消、来源适配与反馈归属：沿用 node:test；把错误、重复请求和部分成功也纳入用例。
- 流式接口：测试数据块拆行、UTF-8 跨块、HTTP 非 2xx、error 事件、缺少终止事件、客户端中断、超时与上游关闭。流结束但未拿到终止状态不能直接标记完成。
- 页面流程：扩展现有隔离 CDP 旅程；本地与 CI 对浏览器路径可配置。Mock 接口只用于隔离回归。
- 真实外部依赖：在目标环境单独检查，保留明确标记的真实验证记录。

新增测试工具只锁定与现有 Vue/Vite/Node 兼容的稳定版本，不在改版时顺手升级整个技术栈。[Vitest 安装要求](https://vitest.dev/guide/)

### 6.3 检索与答案验收

1. 保留原 20 条金标作为回归子集，清楚记录任何数据更新导致的预期变更。
2. 扩至 50 条可回答问题，建议教务 15、考试 10、奖助 15、生活 10；再加至少 10 条未覆盖/歧义问题。
3. 可回答 50 条的首条检索命中率目标不低于 85%；未覆盖/歧义案例应按标注规则拒答或追问，而不是强凑答案。两个分母分开报告。
4. 留出至少 10 条正例在本轮调参时不使用，避免只验证熟悉问题。
5. 人工审读至少 20 条完整回答，检查条件、材料、时间、来源一致性和是否把历史资料当作现行规定。
6. 金标命中率、完整答案评审和真实用户反馈分别报告；任何一个都不被包装成全量真实问答准确率。

### 6.4 性能与媒体

- 新首页不预载数字人视频、语音 SDK 的非必要资源或后台页；视频/讲解面板按需加载。
- 首次发送立即显示处理中状态；检索和生成阶段必须使用真实状态事件。
- 测量页面资源体积、首字时间、总响应时间和取消生效耗时，记录网络、模型与索引模式。
- 在受控 Mock 慢流中，取消后 2 秒内确认上游终止，并保证前端不再追加文字；真实环境另测。
- 同一设备与网络条件比较新旧页面。出现明显回退时先定位，不用更换更快模型掩盖前端问题。

## 7. 发布门槛与交付物

### 7.1 离线/隔离门槛

沿用并扩展现有命令：npm run lint、npm run build、npm run test:server、npm run rag:test:service、npm run release:check、npm run service:journey。新增 test:unit，并明确 release:check 是否已覆盖它，避免手工漏跑。

门禁至少满足：

- 构建、类型和 lint 通过。
- 关键状态单元测试、后端行为测试通过。
- 固定 RAG 回归和新增评估按各自门槛通过。
- 核心旅程及 A01–A29 对应的可自动化/人工项目有记录。
- 关键页面完成相同尺寸 Figma 与浏览器对照，必要时修复后只复查受影响页面。
- 发布证据包含代码版本、执行时间、测试环境和结果，不以旧的 latest JSON 代替本次执行。
- 新增开发依赖和字体/图标资源进入锁文件或资产清单；无临时下载 URL、凭证、测试账号密码进入发布产物。

### 7.2 目标环境门槛

- 真模型、MySQL、SMTP、TTS、官方来源/附件均实际连通。
- 页面深链可刷新，API 不进入前端 fallback，NDJSON 经反代仍逐段返回。
- 管理员初始凭据、会话签名、游客 Cookie 密钥由环境提供；演示内存登录回退不能默认开放到正式环境。
- 首版按现有单实例部署；游客额度和防刷仍是进程内状态，需明确重启边界。若要求重启连续计数或多实例，增加共享存储作为发布前扩展任务，不假装本次本地历史即可解决。
- 数据库变更用新迁移，不执行旧 DROP TABLE 初始化；备份和恢复在测试库演练。
- 本地 hash 索引警告与真实外部服务验证结果分别记录；若产品要求真实语义检索，构建匹配索引并单独验收，不只改 provider 配置。

- 实际发布和外部状态变更在后续实施阶段按当时授权执行；本次只交付计划。

## 9. 回滚与分阶段交付

1. 先保留当前可运行基线和构建产物；每个里程碑记录可恢复版本及依赖锁文件。
2. 页面壳、语音和反馈按模块开放。未通过验收的模块继续隐藏，不展示能点却无效果的按钮。
3. /api 迁移与部署配置作为配套变更；旧后端别名暂保留兼容。回滚同时核对前端版本、后端版本和 Nginx，不能只回退静态文件。
4. 新增反馈表不删除旧表；回滚应用时保留新增数据，避免用删表“回滚”。
5. 会话 schema 升级保留恢复副本；回滚不把多个账号的数据重新合并回旧全局缓存。应准备懂得新身份边界的兼容恢复方案。
6. 如果某阶段阻塞，交付最后一个已验证里程碑，并列出真实未完成项；不将核心演示版称为完整发布版。
7. 本计划执行完成前，39 个任务均保持未完成；Figma 已有设计和旧接口复用不等于对应开发任务已经完成。

## 10. 建议的开始顺序

实际开工先做 **0.1 → 0.3/0.4 → 1.1 → 1.2 → 1.3**；0.2 同步按优先级补齐近期实现所需稿件。最早演示的目标是：首页 → 新问答 → 游客试问 → 登录续问。

不要从整页替换 AgentChat.vue 开始。先固定 API/路由边界和当前成果，再落地视觉，随后把单会话拆成多会话，最后补齐取消、媒体和其他业务模块。这一顺序减少同时改网络、状态与界面造成的定位困难。
